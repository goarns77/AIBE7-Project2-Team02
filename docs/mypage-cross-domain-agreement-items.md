# 마이페이지 연계 교차 도메인 합의 항목

## 1. 문서 목적

이 문서는 마이페이지 내부의 화면 표시, 검색, 필터, 반응형 레이아웃처럼 마이페이지 담당자가 독립적으로 처리할 수 있는 작업을 제외한다.

주문, 제안, 견적 요청, 견적, 채팅, 결제, 정산, 계정 담당자 사이에서 데이터 모델이나 API 계약을 먼저 합의해야 하는 항목만 정리한다. 마이페이지는 원본 도메인 상태를 임의로 변경하지 않고 합의된 읽기 모델을 표시하는 역할로 제한한다.

## 2. 합의가 필요한 항목

### 2.1 거래 완료의 기준

**문제**

현재 마이페이지는 `Payment.COMPLETED`를 완료 거래로 표시한다. 그러나 결제 완료는 주문 준비, 배송, 서비스 제공까지 완료됐다는 의미가 아니다.

**프로젝트 영향**

- 결제 직후 거래가 완료 내역으로 이동해 실제 진행 중인 주문을 찾기 어려워진다.
- 주문 완료 전 리뷰 작성, 정산 확정, 신고 처리 같은 후속 기능이 잘못 열릴 수 있다.
- 계정 탈퇴 제한에서 사용하는 진행 거래 기준과 마이페이지 표시가 달라질 수 있다.

**제시 가능한 방향성**

- 결제 상태와 주문 이행 상태를 별도 필드로 유지한다.
- 마이페이지의 완료 기준은 `Payment.COMPLETED`가 아니라 주문 이행의 `COMPLETED`로 정한다.
- 결제 완료 후 주문 상태는 `CONFIRMED` 또는 `PREPARING`으로 유지한다.

**필요한 합의**

- 주문 담당: 최종 완료 상태와 상태 전이 권한
- 결제 담당: 결제 완료·취소·환불의 의미
- 정산 담당: 정산 생성과 최종 확정 시점
- 계정 담당: 탈퇴를 차단하는 진행 상태 집합

### 2.2 확정 거래 원장과 공통 거래 ID

**문제**

현재 거래는 `Proposal`, `Estimate`, `ChatRoom`, `Quote`, `Payment`, `Settlement`에 분산되어 있다. 직접 견적은 `OrderRequest`와 연결되지 않을 수 있어 모든 경로에 공통으로 사용할 확정 주문 ID가 없다.

**프로젝트 영향**

- 마이페이지에서 같은 거래를 안정적으로 한 건으로 축약하기 어렵다.
- 주문 상세, 리뷰, 신고, 환불, 관리자 조회가 서로 다른 ID를 기준으로 구현될 수 있다.
- 도메인별 휴리스틱 연결이 늘어나고 데이터가 조금만 달라져도 중복 또는 누락이 발생한다.

**제시 가능한 방향성**

- 확정된 `Quote`당 하나의 거래 원장을 생성하고 `quote_id`에 고유 제약을 둔다.
- 거래 원장은 `tradeId`, 구매자 계정 ID, 판매자 프로필 ID, 확정 금액, 이행 상태를 보유한다.
- `orderRequestId`, `proposalId`, `estimateId`, `chatRoomId`는 발생 경로에 따라 선택적으로 연결한다.
- 외부 응답은 내부 참여자 ID 대신 `tradeId`와 사용자 관점의 역할만 제공한다.

**필요한 합의**

- 주문·견적 담당: 거래 원장 생성 시점과 소유 도메인
- 제안·Estimate 담당: 원본 요청 ID 승계 규칙
- 리뷰·신고 담당: 향후 참조할 표준 거래 식별자

### 2.3 제안·견적 요청·견적의 상태 전이

**문제**

`ProposalStatus`와 `EstimateStatus`에는 진행 상태가 정의되어 있지만 실제 상태 변경 API와 자동 전이가 충분하지 않다. 견적 확정 뒤에도 원본 제안이나 견적 요청이 초기 상태로 남을 수 있다.

**프로젝트 영향**

- 마이페이지와 각 상세 화면에 서로 다른 상태가 표시된다.
- 회원 탈퇴의 진행 거래 판정이 종료된 원본 요청 때문에 계속 차단되거나 반대로 진행 거래를 놓칠 수 있다.
- 같은 요청에 여러 판매자가 참여했을 때 선택되지 않은 제안을 어떻게 종료할지 결정할 수 없다.

**제시 가능한 방향성**

- 상태별 변경 주체와 허용 전이를 표로 먼저 확정한다.
- 채팅 시작 시 원본 요청을 `IN_TALK`, 견적 확정 시 선택된 요청을 `ACCEPTED`로 자동 전이한다.
- 동일 주문 요청의 선택되지 않은 제안은 `REJECTED` 또는 별도의 `CLOSED` 정책으로 종료한다.
- 상태 변경은 각 도메인의 명령 서비스가 담당하고 마이페이지는 읽기만 수행한다.

**필요한 합의**

- 제안·Estimate 담당: 상태 전이 규칙과 변경 API
- 채팅·견적 담당: 상태 변경을 발생시키는 이벤트
- 주문 담당: 하나의 요청에서 복수 거래를 허용할지 여부

### 2.4 도메인 간 ID와 연결 규약

**문제**

구매자는 계정 ID를 사용하고 판매자는 계정 ID와 판매자 프로필 ID를 구분한다. 일부 도메인은 `requestId`를 주문 요청 ID가 아닌 구매자 계정 ID 의미로 사용해 이름만으로 식별자 의미를 판단하기 어렵다.

**프로젝트 영향**

- 잘못된 ID 비교로 타 사용자 데이터 노출이나 정상 사용자의 접근 거부가 발생할 수 있다.
- 새로운 API가 어떤 ID를 받거나 반환해야 하는지 담당자마다 다르게 해석할 수 있다.
- Estimate와 Quote 연결을 안전하게 추가하기 어렵다.

**제시 가능한 방향성**

- 필드명을 `buyerAccountId`, `sellerProfileId`, `orderRequestId`처럼 실제 의미에 맞게 명시한다.
- 요청자의 ID는 클라이언트 파라미터가 아니라 JWT와 서버 매핑으로 결정한다.
- 외부 DTO에는 연결에 필요한 리소스 ID만 제공하고 내부 계정·프로필 ID는 숨긴다.
- 기존 의미가 다른 `requestId`는 즉시 변경이 어렵다면 API 문서와 변환 계층에서 명시적으로 분리한다.

**필요한 합의**

- 계정·판매자 담당: 계정 ID와 판매자 프로필 ID 변환 계약
- 주문·Estimate 담당: `requestId`의 표준 의미와 마이그레이션 방식
- API 담당 전체: 외부에 노출 가능한 식별자 목록

### 2.5 금액과 예산의 의미

**문제**

주문 요청과 Estimate의 예산은 `PER_PERSON` 또는 `TOTAL`이지만 Quote와 Payment는 확정 총액을 사용한다. 이를 하나의 `totalAmount` 필드로 합치면 인당 예산이 총액처럼 표시될 수 있다.

**프로젝트 영향**

- 구매자와 판매자가 서로 다른 금액으로 거래를 인식할 수 있다.
- 결제 예정 금액, 매칭 예산, 마이페이지 표시가 불일치한다.
- 향후 할인, 배송비, 수수료, 환불 금액을 추가할 때 필드 의미가 더 불명확해진다.

**제시 가능한 방향성**

- 요청 예산은 `budgetAmount`와 `budgetType`으로 유지한다.
- 확정 견적은 `unitPrice`, `quantity`, `deliveryFee`, `quotedTotalAmount`를 제공한다.
- 결제와 정산은 각각의 스냅샷 금액을 별도 이름으로 제공한다.
- 마이페이지는 원본 금액 종류를 표시하며 임의로 총액으로 재해석하지 않는다.

**필요한 합의**

- 주문·Estimate 담당: 예산 의미와 총예산 계산 규칙
- 견적·결제 담당: 확정 금액과 스냅샷 기준
- 마이페이지 담당: 단계별 금액 라벨과 우선 표시 값

### 2.6 거래 목록 API와 서버 페이징

**문제**

현재 구매·판매 목록은 여러 도메인 데이터를 서버에서 합산하고 메모리에서 정렬한다. 각 도메인이 별도로 페이징되면 단순히 결과를 합치는 방식으로는 전체 최신순 페이지를 보장할 수 없다.

**프로젝트 영향**

- 데이터 증가 시 N+1 조회와 전체 로딩으로 응답 시간이 늘어난다.
- 도메인별 페이지를 합치면 항목 누락, 중복, 페이지 순서 변경이 발생할 수 있다.
- API 응답 계약 변경이 마이페이지 JavaScript와 다른 소비자에게 동시에 영향을 준다.

**제시 가능한 방향성**

- 거래 목록은 주문·거래 도메인이 소유하는 전용 읽기 모델 또는 집계 쿼리로 제공한다.
- 정렬 기준을 `lastActivityAt` 또는 `updatedAt` 하나로 통일한다.
- 페이지 번호보다 정렬 키와 ID를 조합한 커서 방식을 우선 검토한다.
- 응답에 `items`, `nextCursor`, `hasNext`를 포함하고 마이페이지는 이 계약만 소비한다.

**필요한 합의**

- 주문·DB 담당: 읽기 모델 소유권과 쿼리 전략
- 제안·Estimate·견적·결제 담당: `lastActivityAt` 갱신 기준
- 마이페이지 담당: 페이지 크기와 더 보기 UX

### 2.7 채팅방과 거래 생명주기

**문제**

채팅방은 제안 또는 문의에서 시작하고 견적 ID가 나중에 연결된다. 거래가 완료·취소·환불된 뒤 채팅방을 닫을지, 읽기 전용으로 보존할지 정책이 없다.

**프로젝트 영향**

- 완료 거래에서 계속 메시지를 보내 거래 조건이 사후 변경된 것처럼 보일 수 있다.
- 채팅을 닫으면 파일·대화 증빙까지 접근하지 못하는 구현이 생길 수 있다.
- 마이페이지의 채팅 목록과 거래 상세 링크가 서로 다른 생명주기를 갖게 된다.

**제시 가능한 방향성**

- 거래 종료 후 채팅방은 삭제하지 않고 읽기 전용 `CLOSED`로 보존한다.
- 파일과 대화 이력 조회는 거래 참여자에게 계속 허용하고 새 메시지 발행만 차단한다.
- 거래 원장에 대표 `chatRoomId`를 연결하고 마이페이지 이동 경로를 고정한다.

**필요한 합의**

- 채팅 담당: 종료 후 읽기·쓰기 권한과 보존 기간
- 주문·결제 담당: 채팅방을 닫는 상태 또는 이벤트
- 개인정보 담당: 대화·첨부파일 보존 및 삭제 정책

### 2.8 취소·환불·정산 상태

**문제**

견적 거절·철회와 결제 실패·취소는 존재하지만 결제 완료 후 주문 취소, 부분 환불, 정산 취소의 연결 규칙이 없다.

**프로젝트 영향**

- 환불된 거래가 마이페이지에서 완료 거래로 남을 수 있다.
- 구매자 영수증과 판매자 정산서가 실제 금액과 불일치할 수 있다.
- 관리자와 사용자 화면이 서로 다른 최종 상태를 표시할 수 있다.

**제시 가능한 방향성**

- 주문 취소 명령이 결제 취소·환불과 정산 조정을 오케스트레이션하도록 한다.
- `PaymentStatus`, `SettlementStatus`, 주문 이행 상태를 분리하고 허용 조합을 정의한다.
- 부분 환불 가능성이 있으면 변경 가능한 단일 금액 대신 환불 이력 원장을 추가한다.
- 마이페이지는 최종 거래 상태와 결제·환불 보조 상태를 함께 표시한다.

**필요한 합의**

- 주문·결제·정산 담당: 취소 순서, 실패 보상, 재시도 정책
- 관리자 담당: 강제 취소와 분쟁 처리 권한
- 마이페이지 담당: 사용자에게 노출할 상태와 금액

### 2.9 회원 탈퇴와 거래 상태 연계

**문제**

계정 도메인은 여러 도메인의 진행 상태 집합을 직접 조합해 탈퇴 가능 여부를 판정한다. 주문 상태가 추가되거나 기존 상태 의미가 바뀌면 계정 로직이 함께 변경돼야 한다.

**프로젝트 영향**

- 완료된 사용자가 영구적으로 탈퇴하지 못하거나 진행 중인 사용자가 탈퇴할 수 있다.
- 도메인 상태 추가가 계정 서비스에 조용한 회귀를 만들 수 있다.
- 마이페이지 탈퇴 버튼의 안내와 서버 판정이 불일치할 수 있다.

**제시 가능한 방향성**

- 거래 도메인이 `hasActiveTransaction(accountId)` 같은 명시적 포트를 제공한다.
- 활성 상태 집합은 거래 도메인이 소유하고 계정 도메인은 boolean 결과와 차단 사유만 사용한다.
- 완료·취소·환불 이후 활성 거래 해제 조건을 통합 테스트로 고정한다.

**필요한 합의**

- 계정 담당: 탈퇴 정책과 사용자 오류 응답
- 주문·결제·정산 담당: 활성 거래 정의와 해제 시점
- 마이페이지 담당: 차단 사유 표시 방식

### 2.10 운영 DB와 배포 순서

**문제**

엔티티 제약과 코드가 먼저 배포되면 기존 데이터 중복이나 누락 때문에 애플리케이션 시작 또는 런타임 조회가 실패할 수 있다.

**프로젝트 영향**

- 결제 고유 제약 생성 실패, 판매 권한 누락, 상품 소유권 오류가 운영 장애로 이어질 수 있다.
- 담당자별 SQL을 서로 다른 순서로 실행하면 참조 관계가 깨질 수 있다.

**제시 가능한 방향성**

- 배포 전 검증 SQL, 데이터 보정 SQL, 제약 추가, 애플리케이션 배포 순서를 하나의 체크리스트로 관리한다.
- 운영 반영 전에 익명화한 스테이징 복제 데이터로 반복 실행 가능성을 검증한다.
- 장기적으로 Flyway 또는 Liquibase를 도입해 스키마 변경을 버전 관리한다.

**필요한 합의**

- DB·배포 담당: 마이그레이션 도구와 실행 책임자
- 계정·상품·결제 담당: 데이터 보정 기준
- 전체 팀: 실패 시 롤백 절차와 배포 순서

## 3. 우선 합의 순서

1. `결제 완료`와 `거래 완료`의 구분
2. 확정 거래 원장 및 공통 `tradeId` 도입 여부
3. 제안·Estimate·Quote·주문 상태 전이와 변경 주체
4. 취소·환불·정산 및 탈퇴 제한 해제 규칙
5. 금액·ID·페이징 API 계약
6. 채팅 보존 정책과 운영 DB 배포 절차

## 4. 회의에서 확정해야 할 결과물

| 결과물 | 최소 결정 내용 |
| --- | --- |
| 거래 상태표 | 상태 이름, 의미, 변경 주체, 허용 이전·다음 상태 |
| 식별자 관계도 | account, seller profile, request, proposal, estimate, chat, quote, trade, payment 관계 |
| 거래 목록 응답 | 공통 `tradeId`, 사용자 역할, 표시 상태, 금액, 링크, 정렬 키, 페이지 커서 |
| 취소·환불 시퀀스 | 주문·PG·Payment·Settlement 변경 순서와 실패 보상 |
| 탈퇴 판정 계약 | 활성 거래 기준과 완료·취소 후 해제 시점 |
| 배포 체크리스트 | 데이터 검증, 보정, 제약 적용, 코드 배포, 롤백 순서 |

## 5. 마이페이지 단독 처리 범위와의 경계

다음 항목은 위 합의가 끝난 뒤 마이페이지 담당자가 독립적으로 처리할 수 있다.

- 합의된 상태의 한글 라벨과 색상
- 검색·필터·정렬 UI
- 카드 레이아웃과 모바일 대응
- 빈 상태·오류 상태·재시도 UX
- 합의된 상세 URL로 이동

반대로 상태 의미, 거래 완료 시점, 금액 계산, ID 연결, 접근 권한, 취소·환불 규칙은 마이페이지에서 추정하거나 임의 결정하지 않는다.
