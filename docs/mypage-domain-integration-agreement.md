# 구매·판매·오퍼·채팅 통합 작업 합의서

## 1. 목적

외부 작업자가 구현 중인 구매/판매, 오퍼 매칭, 채팅 기능을 현재 계정·마이페이지 기능과 안전하게 합치기 위한 작업 기준이다.

각 담당자는 자신의 항목에서 **무엇을 수정하거나 추가해야 하는지**, **왜 필요한지**, **어떤 상태가 되면 완료인지** 확인한다. 상세 구현 방식과 API 경로는 담당자끼리 조정할 수 있지만, 사용자 식별과 접근 권한 규칙은 변경하지 않는다.

## 2. 공통 합의

### 식별자 기준

| 이름 | 의미 | 기준 테이블 |
|---|---|---|
| `userId`, `buyerId`, `senderId` | 회원 계정 ID | `users.user_id` |
| `sellerId` | 승인된 판매자 프로필 ID | `seller_profiles.seller_id` |
| `requestId` | 구매 요청 ID | `order_requests.request_id` |
| `proposalId` | 판매자가 보낸 오퍼 ID | `proposals.proposal_id` |
| `chatRoomId` | 채팅방 ID | `chat_rooms.chat_room_id` |
| `quoteId` | 협의 견적 ID | `quotes.quote_id` |
| `orderId` | 확정 주문 ID | `orders.order_id` |

### 공통 개발 규칙

- JWT `sub`는 `users.user_id`로 사용한다.
- 요청 본문이나 쿼리 파라미터의 `buyerId`, `sellerId`, `senderId`를 로그인 사용자 정보로 신뢰하지 않는다.
- 현재 사용자의 ID는 서버가 JWT에서 읽는다.
- 판매자 ID는 현재 사용자의 승인된 `seller_profiles`를 서버에서 조회하여 결정한다.
- 개인 데이터는 반드시 소유자 또는 참여자 권한을 확인한 뒤 반환한다.
- 목록 API는 조회용 응답 DTO를 사용하며 엔티티를 직접 반환하지 않는다.
- 외부 기능이 병합되기 전에는 계정·마이페이지 쪽에서 같은 엔티티와 API를 중복 구현하지 않는다.

## 3. JWT 취약점 담당자

### 현재 확인된 문제

- `SecurityConfig`에서 `/api/**`가 `permitAll()`로 설정되어 있다.
- JWT 발급기와 Decoder는 있지만 실제 API 요청 인증에 연결되지 않았다.
- 주문, 견적, 채팅 코드에 임시 사용자 ID가 남아 있다.
- WebSocket 메시지의 `senderId`를 클라이언트가 임의로 지정할 수 있다.

### 수정 또는 추가할 기능과 사유

| 구분 | 수정·추가할 기능 | 필요한 사유 |
|---|---|---|
| 보안 설정 | Spring Security에 OAuth2 Resource Server JWT 인증 연결 | 토큰을 발급해도 SecurityFilterChain이 검증하지 않으면 인증 기능이 실제로 동작하지 않음 |
| 공개 경로 | 회원가입, 로그인, 이메일 중복 확인 등 필요한 경로만 `permitAll()` 처리 | 모든 `/api/**` 허용 상태에서는 비회원도 개인 API에 접근할 수 있음 |
| 보호 경로 | 일반 `/api/**`는 인증 필수, 관리자 API는 `ROLE_ADMIN` 필수로 설정 | 회원 API와 관리자 API의 접근 범위를 분리해야 함 |
| 토큰 검증 | issuer, audience, 만료, 계정 상태, 역할, `token_version` 검증 연결 | 변조·폐기·탈퇴·정지 계정의 토큰 사용을 차단해야 함 |
| 사용자 추출 | 컨트롤러에서 `@AuthenticationPrincipal Jwt`의 `sub` 사용 | 하드코딩 ID와 클라이언트 제공 ID를 제거하기 위함 |
| 판매자 검증 | 승인된 `seller_profiles` 존재 여부를 서비스에서 확인 | `users.role=USER`인 구조에서 실제 판매 가능 여부를 별도로 판단해야 함 |
| WebSocket 인증 | 연결 또는 메시지 처리 시 인증 사용자 확인, `senderId` 서버 지정 | 다른 회원을 사칭한 메시지 전송을 막아야 함 |
| 권한 실패 | 인증 실패 `401`, 권한 부족 `403` 응답 형식 통일 | 화면과 API 테스트에서 오류를 일관되게 처리하기 위함 |

### 완료 기준

- [ ] 토큰 없이 보호 API를 요청하면 `401`이 반환된다.
- [ ] 일반 회원이 관리자 API를 요청하면 `403`이 반환된다.
- [ ] 만료되거나 token version이 다른 토큰이 거부된다.
- [ ] 탈퇴 또는 정지 계정의 기존 토큰이 거부된다.
- [ ] 컨트롤러와 서비스의 하드코딩 사용자 ID가 제거된다.
- [ ] WebSocket 발신자가 JWT 사용자와 일치한다.
- [ ] 공개 API, 회원 API, 관리자 API에 대한 보안 테스트가 통과한다.

## 4. 구매/판매 담당자

### 현재 확인된 문제

- 현재 `order_requests` 엔티티에는 요청 작성자를 나타내는 `buyerId`가 없다.
- 구매 요청 목록 API가 로그인 사용자와 무관하게 전체 데이터를 반환한다.
- 최종 거래를 나타내는 `orders` 도메인이 현재 브랜치에 없다.
- 구매 요청 목록과 확정 구매 목록의 의미가 구분되지 않은 상태다.

### 수정 또는 추가할 기능과 사유

| 구분 | 수정·추가할 기능 | 필요한 사유 |
|---|---|---|
| 구매 요청 소유자 | `order_requests.buyer_id` 추가 및 `users`와 연결 | 내 요청 조회와 수정·취소 권한을 판정하려면 작성자가 필요함 |
| 구매 요청 생성 | JWT `sub`를 `buyer_id`로 저장 | 다른 회원 ID로 요청을 생성하는 것을 막아야 함 |
| 내 요청 조회 | 현재 구매자의 요청만 조회하는 목록 API 추가 | 마이페이지에서 전체 요청이 아닌 내 요청만 표시해야 함 |
| 요청 권한 | 상세, 수정, 취소 시 현재 구매자 소유 여부 확인 | ID만 바꿔 다른 회원의 요청을 조작하는 것을 막아야 함 |
| 확정 주문 | `orders` 엔티티, 저장소, 서비스 및 상태 정의 | 요청과 실제 거래 완료 내역은 별도로 관리해야 함 |
| 구매 내역 | `orders.buyer_id = 현재 userId` 조회 API 추가 | 구매자의 확정 주문 목록을 제공하기 위함 |
| 판매 내역 | `orders.seller_id = 현재 sellerId` 조회 API 추가 | 판매자의 확정 판매 목록을 제공하기 위함 |
| 주문 생성 | 견적 수락 후 주문 생성 및 중복 생성 방지 | 같은 견적으로 주문이 여러 번 생성되는 것을 막아야 함 |
| 목록 편의 | 페이징, 상태 필터, 최신순 정렬 지원 | 데이터 증가 시 전체 조회를 피하고 화면 요구사항을 지원하기 위함 |
| DB 성능 | 구매자·판매자·상태 기준 인덱스 추가 | 마이페이지 목록 조회 성능을 확보하기 위함 |

### 권장 조회 API

| 기능 | 권장 경로 |
|---|---|
| 내 구매 요청 | `GET /api/v1/requests/me` |
| 확정 구매 내역 | `GET /api/v1/orders/purchases` |
| 확정 판매 내역 | `GET /api/v1/orders/sales` |

목록 응답에는 최소한 ID, 제목, 행사 일시, 수량, 금액, 상대방 표시명, 배송지, 상태가 포함되어야 한다.

### 완료 기준

- [ ] 구매 요청 생성 시 JWT 사용자가 `buyer_id`로 저장된다.
- [ ] 구매 요청 상세·수정·취소에 소유자 검증이 적용된다.
- [ ] 구매 요청과 확정 주문이 서로 다른 데이터로 관리된다.
- [ ] 구매자는 자신의 구매 내역만 조회할 수 있다.
- [ ] 승인된 판매자는 자신의 판매 내역만 조회할 수 있다.
- [ ] 같은 견적으로 주문이 중복 생성되지 않는다.
- [ ] 페이징과 상태 필터 테스트가 통과한다.
- [ ] 다른 사용자의 주문 접근 차단 테스트가 통과한다.

## 5. 오퍼 매칭 담당자

### 현재 확인된 문제

- 현재 브랜치에는 `proposals`와 `matching_results` 도메인이 없다.
- 채팅방과 최초 견적 생성 코드가 존재하지 않는 Proposal 데이터를 가정하고 있다.
- 현재 Quote 생성 과정에서 판매자, 수량, 단가, 배송비가 하드코딩되어 있다.
- 오퍼와 채팅 중 수정되는 견적의 역할이 명확히 분리되지 않았다.

### 수정 또는 추가할 기능과 사유

| 구분 | 수정·추가할 기능 | 필요한 사유 |
|---|---|---|
| 매칭 결과 | `matching_results` 저장 및 요청별 조회 기능 | 어떤 판매자 또는 상품이 어떤 기준으로 추천됐는지 보존해야 함 |
| 오퍼 모델 | `proposals` 엔티티, 저장소, 상태 정의 | 판매자의 최초 제안과 이후 거래 흐름의 기준 데이터가 필요함 |
| 오퍼 관계 | `request_id`, `seller_id`, 선택적 `product_id` 연결 | 구매 요청과 판매자 또는 상품의 관계를 추적해야 함 |
| 제안 내용 | 제안 수량, 총액, 메시지, 상태 저장 | 구매자가 오퍼를 비교하고 선택할 수 있어야 함 |
| 보낸 오퍼 | 현재 판매자 기준 오퍼 목록 API 추가 | 판매자가 자신이 보낸 제안을 관리하기 위함 |
| 받은 오퍼 | 현재 구매자의 요청으로 들어온 오퍼 목록 API 추가 | 구매자가 자신의 요청에 대한 제안만 확인하기 위함 |
| 권한 검증 | 오퍼 조회·상태 변경 시 구매자 또는 판매자 확인 | 다른 회원이 오퍼를 열람하거나 수락하는 것을 막아야 함 |
| 상태 전이 | 생성, 수락, 거절, 취소 등 허용된 상태 전이 정의 | 중복 수락이나 완료된 오퍼의 재변경을 막아야 함 |
| 견적 연결 | Proposal을 기준으로 최초 Quote 생성 | 하드코딩된 견적 정보를 실제 오퍼 데이터로 교체해야 함 |
| 채팅 연결 | 오퍼 수락 또는 협의 시작 시 ChatRoom 생성 | 오퍼와 채팅방이 서로 다른 거래로 섞이지 않게 해야 함 |

### 오퍼와 견적 구분

- Proposal은 판매자가 구매 요청에 처음 보내는 제안이다.
- Quote는 채팅 과정에서 변경될 수 있는 견적 이력이다.
- Proposal을 수정할 때마다 덮어쓰기보다 Quote 이력을 새로 저장하는 방식을 권장한다.
- 최종 Quote가 수락되면 Order를 생성하고 관련 상태를 함께 변경한다.

### 권장 조회 API

| 기능 | 권장 경로 |
|---|---|
| 받은 오퍼 | `GET /api/v1/proposals/received` |
| 보낸 오퍼 | `GET /api/v1/proposals/sent` |

목록 응답에는 최소한 `proposalId`, `requestId`, 요청 제목, 판매자 또는 구매자 표시명, 제안 수량, 제안 금액, 메시지, 상태가 포함되어야 한다.

### 완료 기준

- [ ] Proposal이 실제 Request와 Seller에 연결된다.
- [ ] 받은 오퍼와 보낸 오퍼가 JWT 사용자 기준으로 분리된다.
- [ ] 허용되지 않은 상태 변경이 거부된다.
- [ ] 최초 Quote가 하드코딩 값이 아닌 Proposal 데이터로 생성된다.
- [ ] 오퍼별 채팅방과 최종 주문 관계를 추적할 수 있다.
- [ ] 다른 구매자 또는 판매자의 오퍼 접근 차단 테스트가 통과한다.
- [ ] 동일 오퍼의 중복 수락과 중복 주문 생성이 방지된다.

## 6. 채팅 담당자

### 현재 확인된 문제

- 채팅방 엔티티에는 참여자 ID가 있지만 생성 시 요청과 판매자 ID가 하드코딩된다.
- 채팅방 목록 API가 없다.
- 메시지 이력 API에서 현재 사용자의 방 참여 여부를 확인하지 않는다.
- WebSocket 메시지의 `senderId`를 클라이언트 DTO에서 그대로 사용한다.
- 테이블명이 와이어프레임의 `chat_messages`와 현재 코드의 `chat_message`로 다르다.

### 수정 또는 추가할 기능과 사유

| 구분 | 수정·추가할 기능 | 필요한 사유 |
|---|---|---|
| 채팅방 생성 | Proposal에서 `requestId`, `buyerId`, `sellerId` 조회 | 임시 ID를 제거하고 실제 거래 참여자를 연결해야 함 |
| 중복 방지 | 오퍼 하나당 방 하나라면 `proposal_id` UNIQUE 적용 | 동일 오퍼에 여러 채팅방이 생성되는 것을 막아야 함 |
| 채팅방 목록 | 구매자 또는 판매자로 참여한 방 조회 API 추가 | 마이페이지 채팅 목록을 제공하기 위함 |
| 목록 정보 | 요청 제목, 상대방 이름, 최근 메시지, 최근 메시지 시각 제공 | 별도 상세 조회 없이 목록 화면을 구성하기 위함 |
| 메시지 권한 | 이력 조회 전에 현재 사용자의 방 참여 여부 확인 | 채팅방 ID를 바꿔 타인의 대화를 조회하는 것을 막아야 함 |
| 발신자 검증 | `senderId`를 JWT `sub`로 서버에서 지정 | 다른 사용자를 사칭한 메시지를 막아야 함 |
| WebSocket 구독 | 연결·구독·전송 단계에서 참여자 권한 확인 | REST 이력만 보호하고 실시간 구독이 노출되는 문제를 막아야 함 |
| 메시지 검증 | 빈 메시지, 최대 길이, 허용 메시지 타입 검증 | 저장 오류와 악성 또는 과도한 입력을 방지하기 위함 |
| 테이블 통일 | `chat_rooms`, `chat_messages` 이름과 컬럼 확인 | JPA 자동 생성 테이블과 실제 DB 테이블 불일치를 막아야 함 |
| 조회 성능 | `chat_messages(chat_room_id, created_at)` 인덱스 추가 | 방별 메시지 시간순 조회 성능을 확보하기 위함 |

### 권장 조회 API

| 기능 | 권장 경로 |
|---|---|
| 내 채팅방 목록 | `GET /api/v1/chat-rooms` |
| 채팅 메시지 이력 | `GET /api/v1/chat-rooms/{chatRoomId}/messages` |

읽지 않은 메시지 수가 화면에 필요하면 `last_read_at` 또는 별도 읽음 테이블을 추가로 합의한다. 현재 와이어프레임 속성만으로는 최근 메시지 표시는 가능하지만 정확한 미읽음 수 계산은 어렵다.

### 완료 기준

- [ ] 채팅방의 요청, 구매자, 판매자가 Proposal에서 결정된다.
- [ ] 현재 사용자가 참여한 채팅방만 목록에 반환된다.
- [ ] 비참여자의 메시지 조회, 구독, 전송이 모두 차단된다.
- [ ] 저장되는 `senderId`가 JWT 사용자와 일치한다.
- [ ] 같은 오퍼로 채팅방이 중복 생성되지 않는다.
- [ ] 최근 메시지 목록과 메시지 시간순 조회 테스트가 통과한다.
- [ ] 실제 DB 테이블명과 JPA 매핑이 일치한다.

## 7. DB 및 병합 담당 공통 확인

- 기존 개발 환경의 `ddl-auto: update`는 유지할 수 있지만 새 테이블, FK, UNIQUE, 인덱스 SQL을 별도로 공유한다.
- 기존 테이블에 필수 컬럼을 추가할 때는 기존 데이터 보정 후 `NOT NULL`을 적용한다.
- 권장 인덱스는 `order_requests(buyer_id, status)`, `proposals(request_id, status)`, `proposals(seller_id, status)`, `chat_rooms(buyer_id)`, `chat_rooms(seller_id)`, `chat_messages(chat_room_id, created_at)`, `orders(buyer_id, status)`, `orders(seller_id, status)`이다.
- 여러 작업자가 `SecurityConfig`, 공통 예외 응답, 같은 엔티티를 동시에 수정하지 않도록 병합 전에 담당자를 정한다.
- 외부 브랜치 병합 후 전체 계정 테스트와 각 도메인 테스트를 함께 실행한다.

## 8. 마이페이지 연동 시점

아래 조건이 충족되면 계정·마이페이지 담당자가 페이지 연동을 시작한다.

- [ ] JWT 인증이 실제 API와 WebSocket에 적용됐다.
- [ ] 구매, 판매, 오퍼, 채팅 목록 API 경로와 응답 DTO가 확정됐다.
- [ ] 모든 목록 API가 JWT 사용자 기준으로 동작한다.
- [ ] 하드코딩된 구매자와 판매자 ID가 제거됐다.
- [ ] DB 변경 SQL과 인덱스가 공유됐다.
- [ ] 다른 사용자의 데이터 접근 차단 테스트가 통과한다.

연동 대상 페이지는 `/mypage/requests`, `/mypage/purchases`, `/mypage/sales`, `/mypage/offers`, `/mypage/chats`로 한다. 최종 경로는 프론트엔드 라우팅 구조에 맞춰 변경할 수 있다.

## 9. 팀 보고용 요약

| 담당 항목 | 핵심 작업 | 가장 중요한 이유 |
|---|---|---|
| JWT 취약점 | `/api/** permitAll()` 제거, JWT와 WebSocket 인증 연결 | 개인 API 무단 접근과 사용자 사칭 방지 |
| 구매/판매 | 구매 요청 소유자 연결, 최종 주문과 내역 조회 구현 | 내 데이터 조회와 거래 완료 내역 구분 |
| 오퍼 매칭 | Proposal·MatchingResult 구현, Quote·Chat·Order 연결 | 하드코딩 제거와 전체 거래 흐름 보존 |
| 채팅 | 참여자 기준 방 목록·메시지 권한·발신자 검증 | 타인 대화 노출과 메시지 사칭 방지 |

각 담당자는 자신의 완료 기준을 충족한 뒤 API 명세, DB 변경 SQL, 테스트 결과를 함께 공유한다. 계정·마이페이지 담당자는 이를 병합한 후 목록 페이지와 통합 테스트를 진행한다.
